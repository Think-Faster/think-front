# Спек: несколько окон одного раздела, тёмная тема, выбор вместо ввода, аварии по факту

Ветки `TF-Front-Workspace` (§1–4) и `TF-Front-Accidents` (§5). Дополняет [ARCHITECTURE.md](ARCHITECTURE.md), не заменяет его:
структура слоёв (core → entities → stores → features → widgets, `shared/ui`) не меняется.
Источник доменных правил — доменный документ (§1.1, §7.2, §11, §12.5).

## Цели

1. Разделы, которых может понадобиться несколько, открываются в нескольких окнах сразу:
   две карты разных объектов, логи двух объектов рядом, две карточки заявок.
2. Тёмная тема: переключатель в сайдбаре, выбор запоминается, без выбора — как в системе.
3. Рамки у всех полей ввода видны в обеих темах.
4. Там, где у значения есть справочник, поле даёт выбор, а не просит вписать вручную.
   Справочники не хардкодятся в формах — лежат в `*Labels.ts` своей фичи или приходят из BFF.

## 1. Экземпляры окон

Окно на холсте — экземпляр записи реестра (§7.2: `window_id` и `window_type`; §12.5 — дубли
разрешены).

| что | где |
|---|---|
| id экземпляра, номер, лимит `MAX_WINDOW_INSTANCES = 4` | `core/workspace/windowInstance.ts` |
| флаг `multiple` у записи, `findWindowDefinition`, `windowTitle` («Карта 2») | `core/registry/windowRegistry.ts` |
| контекст копии `{objectId?, entityId?}`, localStorage `kontur_instances_v1` | `stores/workspace/instanceStore.ts` |
| `useWindowObject`, `useWindowEntityId`, `openWindowWithObject`, `windowContextSnapshot` | `stores/workspace/windowScope.ts` |
| `openWindowCopy`, очистка контекста при закрытии | `stores/workspace/workspaceCommands.ts` |

Правила:

- Первый экземпляр носит id записи (`map`), копии — `map:2` … `map:4`. Сохранённые раньше
  раскладки остаются валидными.
- Первый экземпляр следует общему выбору (`selectionStore`) и адресу; копия держит свой объект
  или свою сущность и общий выбор не трогает.
- Переход в другое окно («история», «логи» из карточки) идёт через общий выбор к первому
  экземпляру целевого окна — даже если переход сделан из копии.
- «Показать на карте» исполняет только первая карта.
- Карточка (`pred`, `taskDetail`) у первого экземпляра читает `:id` своего маршрута из реестра:
  на `/tasks/:id` карточка прогноза не получает id заявки.
- Содержимое окна узнаёт свой id и маршрут через `WindowInstanceContext`, реестр не импортирует.
- Копию открывает кнопка ⧉ в шапке окна или «+» у выбранного раздела в сайдбаре — с тем, что
  окно показывает сейчас. При лимите — подсказка, окно не открывается.

`multiple: true`: `map`, `queue`, `taskQueue`, `objectHistory`, `dataLog`, `logs`, `pred`,
`taskDetail`. Остальные (настройки, люди, создание заявки) — в одном экземпляре.

## 2. Тёмная тема

- `stores/theme/themeStore.ts`: выбор `light | dark | null` (null — как в системе),
  localStorage `kontur_theme_v1`, атрибут `html[data-theme]`, слежение за
  `prefers-color-scheme`. Подключается в `index.tsx` до первого рендера.
- Переключатель — `.sidebar-theme` в верхней части сайдбара.
- CSS: все цвета — токены в `:root`; тёмные значения задаются дважды —
  `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) {…} }` и
  `:root[data-theme='dark'] {…}`. Компоненты берут цвета только из токенов; литералов цвета
  внутри тёмных блоков нет. Тени и линии — через `--shade-rgb` и `--ink-rgb`.
- Карта: свои токены `--city-*`, `--map-*` на `.map`, с тёмными значениями по той же схеме.
- Сайдбар и шапки окон на градиенте одинаковы в обеих темах.

## 3. Рамки полей

Токены `--field-bg`, `--field-border`. Базовое правило с нулевой специфичностью
(`:where(input:not([type='checkbox'], [type='radio'], [type='range'], [type='color']), textarea)`)
плюс `select`, `.form-card`, `.login-form` — на тех же токенах. Своё оформление поля в фиче
перекрывает базу без `!important`.

## 4. Выбор вместо ввода

Компоненты `shared/ui`:

- `ChoiceField` — выбор из справочника; `allowCustom` добавляет «другое…» с полем ввода для
  открытых справочников (§11: «и т.д.», «прочие»). Значение не из списка не теряется.
  `textChoiceOptions` — справочник без кодов (значение = подпись).
- `ChipMultiSelect` — несколько значений чипами.
- `ChipFilterGroup` — чипы теперь `type="button"` и не отправляют форму.

| поле | откуда варианты |
|---|---|
| заявка: вид работ, классификация неисправности | §11, `taskLabels.ts`, открытые |
| заявка: приоритет | `taskPriorityOptions` 1–5, по умолчанию `TASK_PRIORITY_DEFAULT` |
| заявка: исполнитель, кому вернуть | BFF `/tasks/assignees?role=engineers\|dispatchers` |
| датчик: подсистема, тип | BFF `GET /sensors/types` + `collector.systems`, открытые |
| датчик: пикет | BFF `/objects/{id}/pickets` по цепочке предков (`usePickets`) |
| объект: вид | виды уже заведённых объектов, открытый |
| объект: уровень | не вводится: `parent.level + 1`, у корня 1 (§1.1) |
| инженер: специализация | `engineerSpecializationLabels` (`peopleLabels.ts`) |
| график смен: источник | подписи из данных (график смен, график отпусков), открытый |
| письмо: тип | `emailKindOptions` (fact / forecast — режим рекомендации §11) |
| игнорируемый период: объект, датчик | `useObjects`; датчики выбранного объекта (`useSensors`) |

Остаются текстом: исход и номер тикета инцидента, комментарии, номера документов.

`useSensors(objectId)` грузит датчики объекта целиком (`OBJECT_SENSORS_PAGE_SIZE`): на
коллекторе их за двести, страница BFF по умолчанию — 50.

### BFF

`GET /bff/sensors/types` (`sensors:read`) — различные пары `{system, sType}` из заведённых
датчиков, по порядку. Ветка `TF-BFF-SensorOptions` в think-bff, описание — в
`FRONTEND_INTEGRATION_DOMAIN_MODELS.md`. Там же `picketId` во всех DTO — `number | null`.
При ошибке ручки фронт показывает только `collector.systems` и свободный ввод.

## 5. Аварии и инциденты по факту, маршрут нарушителя

Источник — ML/INTEGRATION.md §13.11 и BFF `/fact-alerts` (`FRONTEND_INTEGRATION_DOMAIN_MODELS.md`).
Модель ведёт эпизод, пока он идёт: `lastAt`, маршрут и подробности растут каждый час; в окне
плановых работ эпизодов нет вовсе.

| что | где |
|---|---|
| типы `temperature`, `blind` (только по факту), `FORECAST_TYPES`, `AlertGroup` | `entities/prediction/types.ts` |
| `FactAlert`: `group`, `lastAt`, `live`, `route`, `detailsJson`, `sensors` (`FactSensor`); `factDetails()` | `entities/factAlert/types.ts` |
| фильтр `live` | `entities/factAlert/factAlertRepository.ts` |
| подписи типов, групп, холод/жара, связь/питание, `factSummary()`, `factSensorsSummary()`, `factSensorLabel()` | `features/predictions/predictionLabels.ts` |
| коэффициенты — только прогнозные типы (`FORECAST_TYPES`) | `features/modelSettings/modelSettingsLabels.ts` |
| идущие эпизоды раз в `LIVE_FACTS_REFRESH_MS` | `features/map/hooks/useLiveFacts.ts` |
| слой маршрута | `features/map/IntruderRoute.tsx` |
| «показать маршрут» из журнала | `showRouteOnMap()` в `features/map/mapRequest.ts` |
| обозначения в названии канала (§11 доменного документа) | `channelHint()` в `features/sensors/sensorLabels.ts` |

Правила:

- Группа: `accident` (пожар, газ, подтопление, проникновение, температура) — тон `high`,
  `incident` (отказы, слепота) — `med`. Группа приходит из BFF, фронт её не выводит сам.
- Журнал данных: чип группы, «идёт», начало и последняя сработка (у прошедшего — «закончилось»),
  подробности одной строкой (`factSummary`), кнопка «Показать маршрут на карте» у эпизода с
  маршрутом — только с правом открыть карту (`objects:read`).
- Где искать: «сработали: <имя датчика> (<пикет>), …», первые несколько, остальные числом —
  в журнале данных, истории объекта и карточке карты. Имя и пикет — из `sensors` (BFF берёт из
  справочника); датчика нет в справочнике — «датчик №N». В каналах температуры — тоже имена.
- `status` эпизода не выводится (служебное, всегда `active`); идёт или кончился — по `live`,
  в истории объекта это значок «идёт»/«закончилось».
- Маршрут на карте — ломаная по датчикам в порядке сработок: номера точек (несколько заходов
  в один датчик — «2·4»), стрелки по ходу, время последнего захода вблизи. Идущий эпизод —
  сплошной с пульсом на последней точке, прошедший — пунктиром. Позиции — из слоя 3
  (`sensorById`) на карте объекта и из раскладки схемы на схеме, даже когда датчики скрыты
  по масштабу. Датчики не из слоя пропускаются.
- Карта сама показывает идущие маршруты коллектора; эпизод из журнала показывается, даже если
  уже не идёт, и кадр приближается к его точкам. Исполняет первая карта.
- Карта района: у коллектора с идущим маршрутом — метка «нарушитель в пути». Легенда
  показывает маршрут, только когда он есть на виде.
- Карточка объекта на карте: «По факту» — идущие эпизоды объекта (у коллектора — и его
  участков) с подробностями; у слепоты — причина, доля каналов и «возможна авария».
- Карточка прогноза объекта в статусе `offline`: «объект не видно — возможна авария».
- Логи: флаг `reading.alarm` — «тревожное сообщение» источника, не тревога системы.
- Название канала в логах и в карточке датчика: подсказка с расшифровкой обозначений.
- Цвет маршрута — токены `--map-route`, `--map-route-ink` на `.map` в трёх местах CSS, как
  у остальных токенов карты.

## 6. Прогнозы: карточка, сводка журнала, права

Источник — BFF `docs/DECISIONS.md` («Прогнозы модели») и `FRONTEND_INTEGRATION_DOMAIN_MODELS.md`,
ML/INTEGRATION.md §2.3 и §9.8.

| что | где |
|---|---|
| `expired`, `alarm`/`alarmEndedAt`, `label`, свидетели с `sensorName`/`picketCode`, `mutedUntil`, `PredictionStats` | `entities/prediction/types.ts` |
| `GET /predictions/stats` | `predictionRepository.getStats()` |
| последний такт модели | `ModelStatus.lastTick` в `entities/modelControl` |
| подписи статусов, `formatProbability`, `formatHours`, `formatRank`, `isRecommendationHeading` | `features/predictions/predictionLabels.ts` |
| сводка над журналом | `features/predictions/PredictionStatsPanel.tsx`, `hooks/usePredictionStats.ts` |

Правила:

- Вероятность в карточке, журнале и истории объекта — только `probability`; `0` — «—». `score`
  вероятностью не называть.
- Журнал: у карточки статус и «тревога держится N ч» / «тревога кончилась <время>». Фильтр
  «Истёкшие».
- Карточка: описание абзацами; «Где смотреть» — датчик, пикет, значение (текст или число), время;
  без свидетелей — «пикет не определён»; признаки модели — подписью, с пометкой, что это важность
  для типа; рекомендация — разделы с заголовками.
- «Заглушить» и «Вернуть на рассмотрение» у заглушённого — только с `predictions:manage`.
  Остальные решения — `predictions:update`. Истёкшую можно вернуть на рассмотрение.
- Заглушённый: «Заглушен до <время>», без права manage — кто может снять.
- Сводка: горит, ждут решения, +новых/кончились за сутки; по типам — горит, в такте модели, ждут,
  в работе, заглушено, ±24 ч. Сверка с тактом — только при совпадении часа; расхождение и
  «модель не подтверждает тревоги больше часа» — красным.

## Открытые вопросы

- Шкала приоритета заявки (1 — наивысший?) не утверждена.
- У вида работ и классификации неисправности нет кодов — хранится подпись; при появлении
  кодов справочник переезжает в `Record<код, подпись>`.
- Подписи видов объекта (`kind`) — сейчас сырые значения из данных.

## Проверка

- `CI=true npm run build` без ошибок и предупреждений (проверяет и типы). Отдельный
  `npx tsc` из проекта (TypeScript 4.9) не разбирает свежий `@types/node`.
- Две карты: у второй свой объект, клик по первой не меняет вторую; «показать на карте» —
  только первая.
- Логи двух объектов рядом; закрытие копии очищает её контекст; после перезагрузки копии
  открываются со своим объектом.
- Пятое окно одного раздела не открывается, видна подсказка.
- Факты (§5): в журнале данных у эпизода «сработали: имя (ПК-…)», без слов `active`/`open`;
  датчик без справочника — «датчик №N».
- Прогнозы (§6): без `predictions:manage` в карточке новой нет «Заглушить», у заглушённого нет
  «Вернуть»; с `manage` — есть. Сводка журнала раскрывается, при разных числах «горит» и «в такте
  модели» — «есть расхождения». Карточка без свидетелей — «пикет не определён».
- Тема: переключатель, перезагрузка, системная тема без выбора; карта и модальные окна читаемы
  в обеих темах; рамки полей видны.
- Формы из таблицы §4 предлагают выбор; неизвестное значение из старых данных не теряется.
- §5: журнал данных показывает группу, «идёт», подробности температуры и слепоты; «Показать
  маршрут на карте» переводит первую карту на коллектор, маршрут виден на карте объекта и на
  схеме с номерами «2·4» у повторного датчика; метка в районе и пункт легенды; карточка объекта
  перечисляет идущие факты. Проверено на локальной заглушке BFF.
